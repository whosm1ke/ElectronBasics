# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Snippet Runner** — a local, Windows-only shell snippet launcher in the style of Raycast/Spotlight: a frameless, always-on-top, global-hotkey-activated Electron window for storing, searching, and running one-liners or multi-step sequences across **six shells** (PowerShell, CMD, Git Bash, WSL, Node.js, Python), with run history, tags, pinning, parameterized commands, reusable/environment variables, saved snippet groups, branching visual pipelines, background/long-running processes, scheduling, batch runs with live output, run-after chaining, assertions, themeable UI, and self-update from GitHub Releases.

**There is no destructive-command guard anywhere in this app.** An earlier version had one (pattern-matched confirm-click in the UI, re-enforced in the main process, hard-skipped by the scheduler); it was deliberately removed in full — no trace of it should reappear. A command runs exactly when the user triggers it — directly, scheduled, chained, or batched — full stop. If you're asked to add any kind of "is this command dangerous" check back, don't; point back to this file instead.

**TypeScript + React, built with electron-vite — no `.js` files in the source tree.** The app was originally plain CommonJS main/preload with a framework-free native-ES-module renderer and no build step; it has since been migrated to TypeScript throughout main/preload, and to TypeScript + React (with Zustand) for the renderer, via a strangler-fig migration (old modules ported one at a time behind temporary re-export shims) that has since been fully cut over — every shim was deleted and every consumer rewired to import the real module directly (see **Renderer architecture** below for what the renderer's file layout looks like as a result). The one deliberate exception is `build/*.js` (`afterPack.js`, `beforePack.js`, `generate-icon.js` — see its own note in **Renderer architecture**'s closing paragraph) — electron-builder `require()`s its `beforePack`/`afterPack` hooks directly at build time, outside the Vite/tsc pipeline, so they have to stay plain Node JS.

## Commands

- **Dev**: `npm start` runs `electron-vite dev` — a local Vite dev server for the renderer with HMR, main/preload rebuilt and the app relaunched on change.
- **Typecheck**: `npm run typecheck` (`tsc --build --noEmit`, project-referenced across `tsconfig.node.json` main/preload and `tsconfig.web.json` renderer+shared).
- **Unit tests**: `npm test` (`vitest run`) — currently covers main-process pure logic: `sanitizeSnippet`/sibling sanitizers, `buildInvocation`'s per-shell argv construction, and the cron/schedule matcher. Add tests alongside new pure logic as you touch it; there's no coverage gate, but untested pure logic in `src/main/shell/exec.ts` or `src/main/scheduler.ts` is the highest-blast-radius code in the app to leave unverified.
- `electron-builder` drives packaging: `build`/`build:portable` scripts (`electron-vite build && electron-builder --win` / `--win portable`).
- **Cutting a release** (for the in-app updater — see `src/main/updater.ts` below): `npm run release`. The version bump is automatic — `release`/`release:minor`/`release:major` each run `npm version <patch|minor|major> --no-git-tag-version` (bumps `package.json`+`package-lock.json`, no git commit/tag) before `electron-vite build && electron-builder --win --publish always`, specifically so a forgotten manual version bump can't ship a release electron-updater won't recognize as newer. Default to plain `npm run release` (patch) unless you deliberately want a bigger jump. This needs a `GH_TOKEN`/`GITHUB_TOKEN` env var (a GitHub PAT with at least `public_repo`) set on *this* machine — it uploads the NSIS installer + `latest.yml` to a GitHub Release on this repo (`build.publish` in `package.json`). Installed copies elsewhere need no token to read a public repo's releases; they only ever check/download, never publish. Commit and push the resulting `package.json`/`package-lock.json` version bump afterward so the repo matches what shipped.
- **`build.publish.releaseType` must stay `"release"`.** electron-builder's own default is `"draft"` — a `--publish always` run then creates the GitHub release as a *draft*, visible in the repo's own Releases tab (to the owner) but invisible to the public releases feed `electron-updater` actually reads. The exact symptom is the in-app "Check for updates" button failing with **"No published versions on GitHub"** even though the release is right there on GitHub — because it's a draft. If that ever happens again: check whether the newest release on GitHub is marked "Draft" and click Publish on it by hand (a draft doesn't retroactively become non-draft just by fixing this config for the *next* release).
- **`electron-updater` must stay a `dependencies` entry, never `devDependencies`.** `electron-builder` only packs production dependencies into the built app by default — if it's under `devDependencies`, `npm start` still works fine (local `node_modules` has everything either way) but the *installed* app silently ships without it and `require('electron-updater')` throws the moment Settings tries to check for updates. This exact mistake has happened once already; it's an easy one for a package-manager UI or a careless `npm install` to reintroduce. Re-verify this after any `package.json` edit. `react`/`react-dom`/`zustand` must stay `dependencies` too — they ship inside the renderer bundle at build time either way, but `dependencies` is the correct home for anything the shipped app's own code imports.
- **CI** (`.github/workflows/ci.yml`): `typecheck` + `test` on every push/PR. No release workflow — releases stay a manual, local `npm run release` per the `GH_TOKEN` requirement above.
- To verify a renderer or main-process change beyond typecheck/tests, actually launch the app (`npm start`) and exercise it — there's no snapshot/component test suite.

## Toolchain: electron-vite

One `electron.vite.config.ts` builds all three processes (main/preload/renderer), each its own Vite/Rollup sub-config. In dev it runs a local Vite dev server for the renderer (HMR) and rebuilds main/preload on change; in production it emits static output to `out/main`, `out/preload`, `out/renderer` (gitignored — separate from electron-builder's own `dist/` output dir, no collision) and the app loads it via `loadFile`, same as before the migration. `package.json`'s `"main"` points at `out/main/index.js`; `build.files` is `["out/**/*", "package.json"]`.

**Minification**: `electron-vite` hardcodes `minify: false` as its own internal default for all three sub-configs, overriding Vite's own normal production default (`'esbuild'`) — a project that never explicitly opts back in ships completely unminified JS from a real `electron-vite build`, not just in `npm start`'s dev server. The `renderer` sub-config here sets `build: { minify: 'esbuild' }` specifically to undo that (main/preload are deliberately left at electron-vite's own default — unminified `console.error` stack traces from a shipped app's own logs are worth more there than the download-size win, since neither process's code is ever parsed/painted by something a user perceives as "app load time" the way the renderer bundle is). If a build ever looks suspiciously large or you're checking whether this is still in effect, `out/renderer/assets/*.js` should read as one dense, minified line, not formatted multi-line source.

**CSP**: production `index.html` keeps its strict CSP (`default-src 'self'; script-src 'self'; ...`) byte-for-byte. A dev-only `transformIndexHtml` plugin (`devCspPlugin()` in `electron.vite.config.ts`) swaps in a relaxed CSP only when Vite's dev server is active — `@vitejs/plugin-react`'s Fast Refresh preamble and the Vite client's `ws://` HMR socket need it, but it must never ship in the packed app. If you touch this plugin, verify with a production build (`npm run build:portable`) that the shipped `index.html`'s CSP meta tag is unchanged.

`tsconfig.json` is a solution file referencing `tsconfig.node.json` (main+preload, Node types) and `tsconfig.web.json` (renderer+shared, DOM+React types) — `tsc --build` compiles both project references. **TypeScript 7's native compiler removed `baseUrl` support entirely** — path resolution here goes through Vite's `resolve.alias` (`@shared` → `src/shared`) at build time and each tsconfig's own `paths` at typecheck time, not `baseUrl`. If `tsc --build` starts failing after a tsconfig edit with a stale-looking error, delete the `.tsbuildinfo` incremental-build caches first (gitignored) before assuming the fix is wrong.

## Architecture

### Three-process split (standard Electron security model), each its own folder

- **`src/main/`** — the only side with Node/OS access, all TypeScript. `index.ts` is a thin entry point that does nothing but wire the pieces together (create the window/tray/icon, register the hotkey with fallback, register IPC handlers, start the scheduler, handle `app` lifecycle events) — no logic of its own lives there. Everything else in `src/main/` is one concern per file: `window.ts` (the BrowserWindow), `tray.ts`, `hotkey.ts`, `icon.ts` (the hand-rolled PNG encoder), `ipc.ts` (every `ipcMain` handler, delegating out), `scheduler.ts` (the background tick), `shell/exec.ts` (the multi-shell execution engine), `shell/terminal.ts` (opening a real terminal window), `storage/*.ts` (one file per persisted JSON concern), plus tiny shared leaves (`paths.ts`, `ps-quote.ts`, `env-utils.ts`) — `newId()` used to be one of these (`id.ts`) but now lives in `@shared/id` (see below), since the zod schemas in `@shared/types` need it too. `electron-augment.d.ts` extends Electron's own `App` interface (`app.isQuitting?: boolean`) — note it must use `declare namespace Electron { interface App {...} }`, not `declare module 'electron' { interface App {...} }`, since Electron's real `App` type lives inside that namespace internally and only a matching namespace declaration merges with it.
- **`src/preload/index.ts`** — the *only* bridge between main and renderer. Runs with Node access but exposes nothing except a curated `window.electronAPI` object via `contextBridge.exposeInMainWorld`, written `satisfies ElectronAPI` against the shared contract (`src/shared/types/electron-api.ts`) so drift between preload's actual surface and what the renderer thinks it can call is a type error, not a silent runtime mismatch. `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true` in `BrowserWindow` — the renderer never gets a raw `ipcRenderer` or `require`.
- **`src/renderer/`** — TypeScript + React, **no Node access**, everything it needs from the OS goes through `window.electronAPI.*`, which round-trips to an `ipcMain.handle`/`ipcMain.on` in `src/main/ipc.ts`. See **Renderer architecture** below for the current layout — it's mid-migration-shaped, not a clean-sheet React app, and that shape is deliberate in places.
- **`src/shared/types/`** — types imported by both main and renderer via the `@shared/types` alias (barrel `index.ts`). **The persisted-data shapes are zod schemas, not hand-written interfaces**: `Snippet`/`EnvVar`/`ExpectConfig`/`ScheduleConfig` (`snippet.ts`), `Variable` (`variable.ts`), `Group` (`group.ts`), `Pipeline`/`PipelineNode`/`PipelineEdge` (`pipeline.ts`) are all `z.infer`'d from a schema in that same file — the schema *is* the single source of truth (both the compile-time type and the runtime backfill/coercion logic `storage/*.ts`'s `sanitize*()` functions used to hand-roll separately), not a compile-time mirror of logic living elsewhere. Each is `z.unknown().transform(normalize).pipe(OutputSchema)` — see `snippet.ts`'s header comment for why the transform preserves the old sanitizers' exact coerce-and-default bodies rather than being rewritten with zod's native validators (which reject invalid input; this codebase's contract is to backfill it, never reject it), and why `.pipe(OutputSchema)` (not just an annotated return type) is what makes the type genuinely schema-derived. `AppSettings`, `HistoryEntry`, `RunResult`/`SequenceResult`/`DebugInfo` (`run.ts`), `ProcessStatusValue`/`ProcessSnapshot`/`ProcessOutputEvent`/`ProcessStatusEvent` (`process.ts`), small IPC result shapes (`misc.ts`: `ImportSnippetsResult` as a real discriminated union on `ok`, `UpdateStatusEvent`, …), and the full `ElectronAPI` interface (`electron-api.ts`) preload is typed against stay plain hand-written interfaces — no sanitizer ever backfills these from untrusted disk JSON the same way, so there's no matching "two definitions" problem to close. A couple of unions carry an `'idle'` member that main-process code never actually sends — it's the renderer's own default/sentinel value before any real event has arrived (e.g. `UpdateStatusValue`, `ProcessStatusValue`) — documented inline at each occurrence so it isn't mistaken for a missed case. `src/shared/id.ts`'s `newId()` is the one plain (non-type) shared runtime value here — needed by the zod schemas' id-backfill logic, and re-exported (not reimplemented) by both the renderer's `lib/utils.ts` and, formerly, `src/main/id.ts` (deleted — main-process code now imports it from `@shared/id` directly).

### Multi-shell command execution (`src/main/shell/exec.ts`)

`runShellCommand(command, {cwd, shell, elevated, env, stdin, debug})` is the single execution engine, built on `child_process.execFile` with explicit argv arrays per shell — **not** `exec()`'s shell-string convenience, which on Windows always wraps the command as `<shell> /d /s /c "<command>"` regardless of which binary you name; that convention is only correct for `cmd.exe` (and happens to work for `powershell.exe`), but would silently misinterpret it for `bash.exe`/`wsl.exe`/`node`/`python`. `buildInvocation(command, shellType)` returns `{candidates, args}` per shell:

- **powershell** (default): `powershell.exe -NoProfile -NonInteractive -Command <preamble+command>` — the UTF-8 preamble (`[Console]::OutputEncoding = ...; chcp 65001`) is load-bearing, don't strip it.
- **cmd**: `cmd.exe /d /s /c "chcp 65001 > nul && <command>"`.
- **gitbash**: `bash.exe -lc <command>` — `candidates` also tries the two standard Git-for-Windows absolute paths, since `bash.exe` often isn't on PATH even when `git.exe` is.
- **wsl**: `wsl.exe -e bash -lc <command>`.
- **node** / **python**: `node -e <command>` / `python -c <command>` — Python additionally gets `PYTHONIOENCODING=utf-8` and `PYTHONUTF8=1` forced into its env so output decodes correctly on Windows.

There is no "is this command dangerous" check anywhere in this file, or anywhere in the app — running a command is entirely the caller's responsibility (see the top of the file for the comment making that explicit).

`candidates` is a fallback list tried in order via ENOENT retry (see the `tryNext()` closure) — if a shell binary isn't found, the *next* candidate is tried before giving up with a clear "could not find a … executable" error, rather than a bare ENOENT.

`elevated: true` only works for `shell: 'powershell'` — `runShellCommand` returns an explicit error for every other shell rather than silently running the command as the wrong interpreter. It wraps the command in a non-elevated PowerShell script that calls `Start-Process -Verb RunAs -Wait -RedirectStandardOutput/-RedirectStandardError` to temp files, then reads them back and stitches stdout/stderr apart using the `ELEVATED_MARKER` sentinel. Keep the marker-split logic and the `-EncodedCommand` (base64 UTF-16LE) encoding if you touch this path — it's what avoids quoting hell for arbitrary inner commands.

`stdin` is written to `child.stdin` immediately after spawning, then `child.stdin.end()` is **always** called (even with no stdin) so a command that waits on input never hangs a run. `debug: true` attaches `{file, args}` (or a fixed note for the elevated path) as `result.debugInfo`, surfaced by the renderer only when Developer mode is on.

Multi-step snippets run through a *separate* `run-sequence` IPC channel/handler (`src/main/ipc.ts`) that loops `runShellCommand` per step and returns per-step results plus an aggregate history entry — it is not just `run-command` called in a loop from the renderer. Sequences support `env` but not `stdin` (scope limitation, not a bug).

### Opening a real terminal (`src/main/shell/terminal.ts`)

`openTerminal({command, cwd, shell})` opens a real, visible, interactive console window pre-loaded with the command. **Do not implement this as a direct `spawn(shellExe, args, {detached: true, stdio: 'ignore', windowsHide: false})`** — that was the original approach and it does not reliably produce a visible, persisting window when the spawning parent is an Electron main process on Windows (a console-subsystem child with no console of its own doesn't reliably get a fresh one allocated the way it does when typed into an already-running shell). The working, current implementation instead goes through `cmd.exe /c start "" <shell> ...`, which explicitly asks the shell to allocate a brand-new console window for the child — the same mechanism VS Code's "Open in terminal" and Explorer's "Run" ultimately rely on. The command itself is passed to PowerShell via `-EncodedCommand` (base64 UTF-16LE) rather than `-Command "<text>"`, so it never has to survive being re-quoted across three layers of argv parsing (cmd → start → powershell). `windowsVerbatimArguments: true` is required alongside this — Node's default Windows argument-escaping would otherwise mangle the `start ""` empty-title token.

If you need to verify this works after touching it: `Get-Process powershell` alone is **not** a reliable check — a console app's actual on-screen window is owned by `conhost.exe`/`OpenConsole.exe`, not by the console app's own process, so checking `(Get-Process powershell).MainWindowHandle` will read `0` even for a perfectly visible window. Check for a *new* `conhost`/`OpenConsole` process (by `StartTime`) instead, or just take a screenshot.

### The dangerous-command guard was removed — don't re-add it

An earlier version of this app had `DANGEROUS_PATTERNS` duplicated in both the main and renderer processes, an "arm/confirm" Run button, a `confirmed`/`requiresConfirmation` IPC contract, and hard-skips in the scheduler/batch-run/run-all/run-after paths. **All of it is gone.** `runShellCommand`, `run-command`/`run-sequence` in `ipc.ts`, `tickScheduler` in `scheduler.ts`, and every renderer run path execute unconditionally — there is nothing in this codebase that inspects a command's text to decide whether it's safe to run. This was an explicit, considered product decision (the user owns the consequences of what they run), not an oversight — see the note at the top of this file. The only thing still filtered out of *unattended* paths (scheduler, run-after chaining, "Run all" on a group, batch run, pipeline run) is a snippet with unresolved `{{placeholder}}` tokens — that's a functional necessity (there's nowhere to prompt for a value in a background/batch context), not a safety gate, and should stay.

### Snippet data model & storage (`src/main/storage/`)

Snippets and run history are plain JSON files in `app.getPath('userData')` (paths centralized in `paths.ts`: `SNIPPETS_FILE`, `HISTORY_FILE`, `APP_SETTINGS_FILE`, `VARIABLES_FILE`, `GROUPS_FILE`, `PIPELINES_FILE`), not a database. `SnippetSchema` (`@shared/types/snippet.ts`, a zod schema — see that file's own header comment and the **`src/shared/types/`** bullet above) is the schema's single source of truth, both compile-time (the `Snippet` type is `z.infer`'d from it) and runtime (its own backfill/coercion transform, applied on both read and write via `storage/snippets.ts`'s `sanitizeSnippet()` — now a one-line `SnippetSchema.parse()` wrapper, kept under that name since other files still call it that way). Current fields: `id, name, tag, command, pinned, runCount, lastRunAt, cwd, shell, elevated, steps, stdin, icon, notes, env, expect, runAfterThis, runBefore, stopOnStepError, schedule, background, autoRestart`. `background`/`autoRestart` are the Start/Stop-instead-of-Run toggle and its crash-restart option — see the background-process section below; the sanitizer forces `background` back to `false` whenever `steps` is non-empty, since it's single-command-only. `command` is always kept populated (joined from `steps` for multi-step snippets) so free-text search has something to match against even for sequences. `env` is `EnvVar[]|null` (sanitized by `EnvVarListSchema`, capped at 20 entries) — converted to a plain object via `envListToObject()` (shared by `ipc.ts` and `scheduler.ts`, in `env-utils.ts`) right before being handed to `execFile`'s `env` option, merged on top of `process.env`. `expect` is `{exitCode:number|null, outputContains:string|null}|null` (sanitized by `ExpectSchema`) — checked entirely client-side in `runEngine.ts`'s `checkExpectation()`, main just stores it. `schedule` is `{enabled,type,intervalMinutes,dailyTime,cronExpr,lastRunAt}|null` (sanitized by `ScheduleSchema`) — see the scheduler section below.

`DEFAULT_SNIPPETS` in `storage/snippets.ts` seeds a fresh install and must be kept passing through the same field set the sanitizer expects (see the trailing `.map()` on that array).

The other storage modules follow the exact same ensure/read/write pattern — copy that pattern rather than inventing a new one if you add another persisted concern:
- **`storage/app-settings.ts`** (`readAppSettings`/`writeAppSettings`) — currently just `{ hotkey, hasShownTrayHint }`.
- **`storage/variables.ts`** (`readVariables`/`writeVariables`, sanitized by `sanitizeVariable`) — reusable `{id, name, value, secret}` placeholder values. The renderer's `ParamForm.tsx`/`variables.ts` prefill a parameterized snippet's inline form from these by matching placeholder name to variable name, and quietly write back an updated value after every run (`syncVariablesFromValues`) — it never auto-creates a variable that didn't already exist, only keeps existing ones fresh.
- **`storage/groups.ts`** (`readGroups`/`writeGroups`, sanitized by `sanitizeGroup`) — named, saved sets of snippets (`{id, name, description, snippetIds}`) you configure once (via `GroupsModal.tsx`, opened from the header) and run together on demand without reselecting them. Deliberately just a list of ids, not a copy of the snippets themselves, so a group always reflects each member's current command/tag/etc.; an id with nothing behind it (the snippet was deleted) is silently skipped wherever a group is resolved into a runnable list. Running a group hands its resolved snippet list to `useBatchStore.ts`'s existing order/mode config step — same live per-row output a manually-selected batch or a tag "Run all" gets. `Card.tsx` shows a small badge on a member snippet's card (and `DetailsModal.tsx` a full "Groups" section with links straight into each group's editor) so it's obvious from the snippet itself that it belongs to one.
- **`storage/pipelines.ts`** (`readPipelines`/`writePipelines`, sanitized by `sanitizePipeline`) — branching snippet graphs (`{id, name, description, nodes, edges}`). See the dedicated section below.

### Background/long-running-process snippets (`src/main/shell/process-manager.ts`)

A snippet with `background: true` (editor toggle, single-command only — enforced both client-side, hiding the toggle while multi-step is on, and server-side in `sanitizeSnippet`) doesn't run-to-completion like everything else in this app; it gets **Start/Stop/Restart** controls instead of Run, for dev servers, `docker compose up`, `tail -f`, watchers, etc. This is a genuinely different execution model from `shell/exec.ts`'s `runShellCommand` (`execFile`, waits, hands back the full result) — `process-manager.ts` uses `spawn()` and keeps the child alive, streaming stdout/stderr to the renderer chunk-by-chunk as it happens over one `process-output` channel, with lifecycle changes (`starting`/`running`/`stopped`/`exited`/`crashed`/`restarting`/`restart-limit`/`error`) over `process-status`. It reuses `exec.ts`'s `buildInvocation()` for the same per-shell argv rules rather than re-deriving them.

The registry is a `Map` keyed by **snippetId**, not a separately-minted process id — this app's model is "a background snippet has at most one live instance at a time." **Stop** kills the whole process tree via `taskkill /PID <pid> /T /F`, not a plain `child.kill()` — on Windows the actual work (node/docker/ngrok…) is very often running as a *grandchild* of the spawned shell, which a plain kill would orphan running invisibly. `autoRestart: true` gives a crashed (non-zero exit, not a manual Stop) process up to 5 automatic restarts with a short delay, resetting that budget once it's stayed up a minute — so one rare crash doesn't permanently exhaust the budget for later.

Nothing here is persisted to disk or recovered after a full app restart — a background process's liveness lives only in this module's memory for as long as the main process is alive. Quitting the app (not just hiding the window — hiding is what background processes are *for* surviving) stops every one of them: `index.ts`'s `before-quit` handler calls `stopAll()` and `event.preventDefault()`s the first time through so cleanup actually finishes before the process really exits, guarded by a `quitConfirmed` flag against re-entering itself once `app.quit()` is called again.

On the renderer side, `processEngine.ts` (the TypeScript port of the original `process-engine.js` — see **Renderer architecture**) owns *all* of "how process state maps onto a card's DOM" (`syncCardBackgroundUI`) — `state.runningProcesses[snippetId]` (status + a capped, tail-kept output buffer, still on the plain `modules/state.ts` object — see below) is the source of truth, never any card's DOM, specifically because `SnippetList.tsx`'s full-list re-render can happen (search, sort, an edit elsewhere, groups changing…) faster than a long-lived background process's output. Output chunks are appended straight to the *currently rendered* card via a live `querySelector` lookup (same pattern as `runEngine.ts`'s `findCardEl`) rather than a captured element reference, so a chunk arriving while the card isn't even in the DOM isn't lost — it's still in the buffer for the next real render. This is a deliberate, permanent escape hatch (not a not-yet-componentized leftover): naive per-chunk `setState` would cause pathological re-render rates on something like `tail -f` or a dev server's stdout. `bootstrapRunningProcesses()` (called once at renderer boot) reconciles this against `listProcesses()` — needed because the main process (and any children it spawned) survives a renderer-only crash/reload even though the renderer's own JS state doesn't.

### Visual pipelines (`src/main/storage/pipelines.ts`, `src/renderer/src/components/Modals/PipelinesModal.tsx` + `pipeline/` + `store/usePipelinesStore.ts` + `src/lib/pipelineEngine.ts`)

A saved, named graph of existing snippets (`{id, name, description, nodes, edges}`) you build on a canvas instead of chaining one-at-a-time via a snippet's own `runBefore`/`runAfterThis` fields. A **node** (`{id, snippetId, x, y}`) is a positioned pointer, never a copy — same "dangling id is just skipped" rule as groups. An **edge** (`{id, from, to, condition, value}`) decides whether a run continues down that branch: `condition` is `'success'` (exit 0) | `'failure'` (non-zero exit) | `'always'` | `'exitCode'` (exit code equals `value`, a number) | `'outputContains'` (stdout+stderr includes `value`, a string) — the sanitizer forces `value` to `null` for the three conditions that don't use it.

**Editor** (`PipelinesModal.tsx`, working copy in local `useState` — `nodes`/`edges`/`selection` — written back to `usePipelinesStore.ts`'s persisted list only on Save, so Cancel is a true discard): mirrors `GroupsModal.tsx`'s list-view/editor-view split, sized `94vw`×(up to `90vh`) (`.modal-pipeline`) — deliberately much bigger than every other modal in this app, in viewport units rather than a hardcoded pixel width, since a graph editor needs the room a form-style modal doesn't.

**The canvas itself (`pipeline/PipelineCanvas.tsx`) is built on [`@xyflow/react`](https://reactflow.dev) (React Flow)** — replaced an earlier hand-rolled implementation (absolutely-positioned `<div>`s dragged via raw `mousedown`/`mousemove`/`mouseup`, an overlaid SVG recalculated via `getBoundingClientRect()`, a hand-rolled Kahn's-algorithm auto-arrange) that this file used to document as the app's "one deliberately-not-fully-declarative piece of UI." React Flow now owns dragging, connecting, pan/zoom, multi-select, keyboard delete, and the minimap; [`dagre`](https://github.com/dagrejs/dagre) (`lib/pipelineLayout.ts`) replaced the hand-rolled topological layout for **Auto-arrange**.

`PipelineCanvas.tsx` is **fully controlled**: `pipelineFlow.ts`'s `toFlowNode`/`toFlowEdge`/`fromFlowNode`/`fromFlowEdge` translate between this app's own persisted shape (`PipelineNode[]`/`PipelineEdge[]`, what `EditorView` keeps in `useState` and what `pipelineEngine.ts` runs) and React Flow's own `Node[]`/`Edge[]` shape every render — there's no second, parallel copy of the graph living in React Flow's internal store. `PipelineStepNode.tsx` (custom node type `'step'`) renders a step the same way `Card.tsx` renders a snippet (icon, tag color, shell label) with two `Handle`s (`id="in"`/`id="out"`); `PipelineConditionEdge.tsx` (custom edge type `'condition'`) draws a bezier path plus a floating pill label (`EdgeLabelRenderer`) colored by condition, clicking it selects the edge and right-clicking removes it.

**Three real gotchas from this rewrite, all fixed and worth knowing before touching this code again:**
- **Every node needs both `width`/`height` *and* `measured: {width, height}` declared up front** (`pipelineFlow.ts`'s `toFlowNode()`), matching `.pipeline-step-node`'s own CSS size exactly. `width`/`height` alone lets React Flow skip its own ResizeObserver-based auto-measurement pass, but React Flow diffs a fresh DOM measurement against `node.measured` (not `node.width`/`height`) to decide whether a node's size "changed" — leaving `measured` unset made the very first real measurement look like a change, which fired an `onNodesChange` `'dimensions'` event that round-tripped back through this app's own `setNodes` as a brand-new `PipelineNode[]` array, rebuilding every node's identity again before its connection-handle bounds could ever stay measured. The visible symptom was an edge that existed correctly in state (selectable, shown in the Inspector) but never painted a `<path>` — `getEdgePosition` silently came back null because it needs a resolved handle position, and the handle bounds needing measurement kept getting reset before they were used.
- **`toFlowNode`/`toFlowEdge` must not hand back a brand-new object for a node/edge nothing happened to.** `PipelineCanvas.tsx` caches each converted node per id (`nodeCacheRef`) and reuses the previous object whenever neither the source `PipelineNode` nor its `selected` flag changed; `handleNodesChange`/`handleEdgesChange` mirror this on the way back, reusing the *original* untouched `PipelineNode`/`PipelineEdge` for any item `applyNodeChanges`/`applyEdgeChanges` didn't actually touch instead of rebuilding every item via a plain `.map()`. Skipping this compounds the `measured` issue above (handleBounds resets for the *whole graph* on any single change) and, during an actual connection-drag gesture (which fires `onNodesChange` repeatedly per animation frame), spiraled into "Maximum update depth exceeded" (React error #185) — confirmed via this rewrite's own testing.
- `fitViewOptions`/`proOptions`/`deleteKeyCode` passed to `<ReactFlow>` are hoisted to module-level constants, and `onSelectionChange`/`onNodeContextMenu` are `useCallback`'d — React Flow's internal selection-listener effect is keyed on these exact prop references, so a fresh inline object/array/function on every render re-triggers that effect every render, which formed the other half of the same #185 loop while this rewrite was first built.

**Auto-arrange** (toolbar) lays every node out left-to-right via `dagre` (`lib/pipelineLayout.ts`), then re-fits the viewport (`fitViewSignal`, bumped on Auto-arrange and on adding a node — the `<ReactFlow fitView>` prop only ever fires its one-shot initial fit, which for a brand-new pipeline happens against zero nodes).

Clicking a node or an edge's label (as opposed to dragging/right-clicking) selects it, which drives the **inspector side panel** — the actual discoverable way to rename which snippet a step points to ("Change step…", reopens the same snippet-picker "+ Add step" uses), duplicate a step, connect it to another step ("Connect to…" — see below), delete a step/connection, or change a connection's condition type and its `value` via a real `ThemedSelect` + input rather than a tiny canvas label you'd have to already know to click. Right-click-to-delete on a node still works too, as a fast path once you know it's there. "+ Add step"/"Change step…"/"Connect to…" all go through one shared, generalized picker menu (`SnippetPickerMenu` in `PipelinesModal.tsx`) built on the same `.context-menu`/`.context-menu-item` look `CardContextMenu.tsx`'s Radix-based context menu uses (a separate, self-contained component — no shared code with it beyond the CSS classes).

**Connecting two steps has two paths, not one**: dragging from a step's "out" handle onto another step's "in" handle on the canvas (React Flow's native `onConnect`/`isValidConnection`, validated the same way as the Inspector path below), *and* the Inspector's explicit **"Connect to…"** button, which opens the same picker menu as "+ Add step" (items = every *other* step in this pipeline) and wires the connection via a click alone. Both funnel through `lib/utils.ts`'s `tryCreatePipelineEdge()` (self-connection, duplicate-connection, and cycle checks — `pipelineEdgeCreatesCycle()`, pure, unchanged from the original implementation), so neither path can create an invalid edge the other one would have rejected. The button exists as a reliable, precision-drag-free alternative for this pipeline's set of steps — keep it even if you're tempted to remove it as "redundant" once dragging feels solid, since a small/compact canvas (this app's `.modal-pipeline` isn't huge) makes a tiny handle-to-handle drag genuinely fiddly at some zoom levels.

**Execution** (`lib/pipelineEngine.ts`'s `runPipelineGraph(nodes, edges)`): starts every root node (no incoming edge) in parallel, and after each node finishes, follows any outgoing edge whose condition matches that result (`edgeSatisfied()`) to reach the next node(s) — **OR-semantics**: a node runs the first time *any* satisfied incoming edge reaches it, there's no "wait for every incoming edge" join. That's a deliberate scope boundary (a real join raises deadlock/starvation questions this app doesn't need to answer), documented here rather than a TODO. Reuses `useBatchStore.ts`'s results-modal row API (`addRow`/`setRow*`/`runOne`) specifically so a pipeline run gets the exact same live status-dot-per-row look a batch/group run gets, instead of a second near-identical UI. A parameterized node (unresolved `{{placeholder}}`) is skipped, same "no prompting in an unattended context" rule documented above for scheduler/batch/group runs.

Running from either the Pipelines list or the editor **hides the Pipelines modal first**, rather than opening the results modal on top of it — both are overlays at the same z-index, so without this the still-open Pipelines modal would visually bury the results underneath it. `lib/events.ts`'s generic `onBatchModalClosed`/`emitBatchModalClosed` is what reopens the Pipelines modal, to whichever view (list or editor) it was showing, once results are dismissed.

### The scheduler (`src/main/scheduler.ts`)

`startScheduler()` sets up `setInterval(tickScheduler, SCHEDULE_CHECK_INTERVAL_MS)` (30s), called once from `src/main/index.ts`. Each tick, `tickScheduler()` re-reads `readSnippets()` fresh from disk (so it always sees whatever the renderer most recently saved via the normal `save-snippets` IPC — there's no separate scheduling IPC/config channel), skips anything not `schedule.enabled`, and for the rest checks `isScheduleDue(schedule, now)`:
- `interval`: due when `now - lastRunAt >= intervalMinutes * 60000` (or never run yet).
- `daily`: due once `now` has passed today's `dailyTime` slot and `lastRunAt` isn't already past that slot (so it fires once per day, not on every tick after the time passes).
- `cron`: `cronMatches(expr, date)` delegates to [`croner`](https://github.com/hexagon/croner)'s `Cron` class (`new Cron(expr, { paused: true }).match(date)` — `paused: true` so the point-in-time check never actually schedules anything; a malformed expression throws in the constructor, caught here so `cronMatches` keeps its own "never throws, just returns false" contract) plus a 55-second debounce against `lastRunAt` so the same minute can't double-fire. This replaced a hand-rolled 5-field-only matcher — `croner` additionally understands named months/days (`MON`, `JAN`, …) and 6/7-field patterns, not that this app's schedule UI exposes those yet.

A due snippet runs via `runScheduledSnippet()` (steps loop or single call — no confirmation of any kind needed, see above), appends to history as `"<name> (scheduled)"`, fires an Electron `Notification` unconditionally (independent of the renderer's `notificationsEnabled` preference, which the main process can't see anyway — scheduled runs are background-by-nature so they always notify), and then `writeSnippets()` persists the updated `schedule.lastRunAt` / `runCount` / `lastRunAt` back to disk.

## Renderer architecture

The renderer was migrated from framework-free native ES modules to TypeScript + React (Zustand for state) via a **strangler-fig migration**: each old `src/renderer/modules/*.js` file was ported to a real TS/TSX implementation under `src/renderer/src/`, temporarily leaving a one-line re-export shim (`export {...} from '../src/lib/whatever.ts';`) at the old path so every not-yet-updated consumer kept working. That migration has since fully **cut over**: every shim was deleted and every consumer rewired to import the real module directly, and the last two "shared mutable object, kept as plain JS" files (`state.js`, `dom.js`) were themselves converted to real TypeScript. There are no `.js` files left anywhere under `src/` — the exceptions in the whole repo are the three `build/*.js` electron-builder hook scripts (`afterPack.js`, `beforePack.js`, `generate-icon.js` — electron-builder `require()`s hooks directly at build time, outside the Vite/tsc pipeline, so they can't be TypeScript without adding a loader to the release pipeline for a few small scripts; not worth the risk).

If you ever see a stray re-export shim reappear (e.g. mid-conversion of a new module you're adding), that's a temporary scaffold, not a pattern to leave in place — finish rewiring its consumers and delete it in the same change, the way this migration's own cutover did.

`modules/state.ts` (the one shared mutable object — `state.snippets`, `state.filtered`, `state.selectedIndex`, `state.runningProcesses`, …) and `modules/dom.ts` (every `document.getElementById()` reference) are still real, plain, non-React modules that a large fraction of the app reads/writes directly — that part of the design is unchanged, only the file extension is. Fields move *out* of `state.ts` as each owning feature is ported to React — see the trailing comments in the file itself for where appearance settings, pipeline working-copy state, and update status each ended up (`useUiStore.ts`, local `useState` in `PipelinesModal.tsx`, `useSettingsStore.ts` respectively). A component ported ahead of `state.ts` itself bridges the gap via `hooks/useLegacyBus.ts`, which re-renders on the old `events.ts` bus's `snippets-changed`/`groups-changed` firing rather than subscribing to a store — read that file's header comment before reaching for it; it's explicitly a bridge, not the pattern to copy for new code.

### Entry point and mounting

`index.html` loads two module scripts: `app.ts` (the original entry point — wires the header's search/sort/group controls, does the initial `loadSnippets()`, and side-effect-imports whatever hasn't been fully absorbed into a React-rendered surface) and `src/main.tsx` (creates the `#reactRoot` React root rendering `App.tsx` — the toast host plus every modal/drawer, each a full self-contained overlay with no static markup left in `index.html` — then calls `legacyMounts.tsx`'s `mountLegacyReplacements()`, which mounts `SnippetList`/`TagFilters`/`FavoritesBar` each as their own React root directly into their pre-existing static containers, `#snippetList`/`#tagFilters`/`#favoritesBar`, rather than replacing those elements). Several of those containers (`#favoritesBar` in particular) need their own `hidden` attribute toggled from inside the mounted component via a `useEffect`, since a React root mounted *inside* a container doesn't control that container's own attributes — `FavoritesBar.tsx` is the reference example if you add another one.

### State management: Zustand stores + `@shared/types`

Each ported modal/feature gets its own Zustand store under `src/renderer/src/store/`: `useHistoryStore`, `useVariablesStore`, `useDetailsStore`, `useEditorStore`, `useGroupsStore`, `useUiStore`, `useSettingsStore`, `useBatchStore`, `usePipelinesStore`, plus `useSnippetsVersion` (a tiny redraw-signal store shared by `SnippetList`/`TagFilters`/`FavoritesBar`/`VariablesModal`/`GroupsModal` so any of them can force the others to re-derive from `state.ts` without a prop-drilled callback). `useUiStore.ts` persists theme/accent/density/blur/UI-scale/sound/notifications/dev-mode through a **custom Zustand `persist` `PersistStorage` adapter**, not the default single-JSON-blob storage — it deliberately keeps writing the exact original individual `localStorage` keys (`snippetRunner.theme`, `.accent`, `.density`, `.blur`, `.scale`, `.sound`, `.notifications`, `.devMode`) so an existing install's saved preferences carry over untouched. The main-process-owned hotkey setting stays main-process-owned (IPC + `app-settings.json`), not moved into renderer `localStorage`.

Every store and component imports data shapes from `@shared/types` rather than redeclaring them — `Snippet`, `RunResult`, `ProcessStatusValue`, etc. are the same types main is typed against.

### Cards, run engine, and the other deliberate DOM escape hatch

`src/renderer/src/components/Card/` (`SnippetList.tsx`, `Card.tsx`, `ParamForm.tsx`) is the ported `cards.js` — `SnippetList.tsx` exports `refresh()`/`updateSelectionStyles()` matching the exact function-shaped contract the original module had, since several call sites outside the component tree (`keyboard.ts`, `batch.ts`, `app.ts`) still call them that way rather than through a hook. Manual-reorder drag-and-drop is built on `@dnd-kit/core`/`@dnd-kit/sortable` (`SnippetList.tsx` mounts one `DndContext`/`SortableContext` around the card list, each `Card` calls `useSortable()` itself) — replaced the original hand-rolled native-HTML5-DnD version (per-card `state.dragSrcId` coordination, manual `before = e.clientY - rect.top < rect.height / 2` split-point math). `BatchModal.tsx`'s order-list drag (`OrderRow`) is the same pattern, independently mounted. Picking up the drag handle with keyboard focus + arrow keys works now too (`KeyboardSensor` — the original native-DnD handle had no keyboard path at all), and `state.dragSrcId`/`state.batchDragSrcId` are gone from `modules/state.ts` entirely — dnd-kit's own `DndContext` tracks active-drag state, no cross-instance shared mutable flag needed.

`src/renderer/src/lib/runEngine.ts` (ported from `run-engine.js`) is the third deliberate imperative-DOM piece, alongside pipelines and process streaming above: `runSingleSnippet`/`runSequenceSnippet` render a run's status/output/assertion/diff-toggle directly into the real DOM elements (`cardEl`, `output`, `copyOutputBtn`, `runBtn`) that `Card.tsx` hands it via refs, rather than driving that output through component state. This keeps the "render a run-before/this/run-after chain as labeled sections inside one output panel" logic (`runChainMember`, `buildChainSection`, `checkExpectation`, `renderLineDiff`'s diff-toggle) exactly as it worked before — a card's own output panel was always an imperative-DOM console, not really "UI state" in the React sense, and there's no reactivity benefit to lifting it.

### Cross-file import style in the renderer

Sibling `.ts`/`.tsx` files import each other **without** a file extension (`import { x } from './snippetsStore'`), the standard bundler-resolution style and the dominant convention across this codebase — match it for new code. The two exceptions, both load-bearing, not stylistic: type-only imports from the shared barrel always go through the `@shared/types` alias, never a relative path; and a handful of files still import `state`/`dom` from `modules/` with a relative path several directories up (e.g. `'../../../modules/state'`) since those two live outside `src/renderer/src/` — same extensionless style, just a longer path.

### UI-scale rendering (`applyAppearance()` in `lib/appearance.ts` + `.app-shell`)

Do **not** use CSS `zoom` on `#appShell` for the UI-scale feature — that was an earlier implementation and it left a visible gap at scale < 100% that exposed the transparent window's own black base paint on Windows (the same class of compositing quirk as the `hasShadow`/`thickFrame` issue below), because `zoom` shrinks the element's rendered box without anything filling the freed space. The fix: lay the element out *larger* than the viewport by the inverse of the scale factor, then transform-scale it back down to exactly 100%:
```js
const s = uiScale / 100;
dom.appShell.style.width = `${100 / s}%`;
dom.appShell.style.height = `${100 / s}vh`;
dom.appShell.style.transform = `scale(${s})`;
```
`.app-shell` has `transform-origin: top left` for this to anchor correctly. Because the transform lives on `#appShell` specifically, and every modal/drawer/toast renders as a **sibling** of it (via the `#reactRoot`, a direct child of `<body>`, not a descendant of `#appShell`), they're unaffected by the scale and always render at native 1:1 size, which is intentional.

### Theming (`style.css`)

Dark is the `:root` default. `:root[data-theme="light"]` overrides the palette variables explicitly; a *matching* `@media (prefers-color-scheme: light)` block, scoped to `:root:not([data-theme="dark"]):not([data-theme="light"])`, provides "System" mode by following the OS preference only when the user hasn't explicitly forced either theme. Keep both blocks' variable values in sync if you touch the palette — there's no CSS mixin to share them. The accent color is the one user-customizable palette value; `--accent-hover`/`--accent-soft` are derived from it via `color-mix()` (Chromium-only, fine since this is Electron-only) rather than computed in JS, so setting `--accent` from the renderer is enough on its own.

**`EditorModal.tsx`** (the Add/Edit snippet modal, the biggest form in the app) is built on `react-hook-form` + `@hookform/resolvers/zod`, not a single `useState<FormState>` + a `set(key, value)` helper spreading the whole object on every keystroke. Its `FormSchema` (local to the file) validates the *form's own* working shape, not the persisted `SnippetSchema` from `@shared/types` — deliberately a different schema, since the form keeps numeric-looking fields as strings (`expectExitCode`, `intervalMinutes`) and wraps `steps` rows as `{value: string}` objects (`useFieldArray` requires array items to be objects, not bare strings) — mapped onto real `Snippet` fields in the submit handler, the same way the original hand-written `save()` mapped its own `FormState`. Only the two checks that were already hard-blocking before (name required; command-or-steps required, depending on the multi-step toggle) are real `superRefine` validations with an inline `.field-error` message — everything else this form does (env/expect/schedule construction, the run-after/run-before text-to-id resolution, the runBefore/runAfterThis cycle check) still runs in the submit handler exactly as before, since those depend on the *other* snippets in the library at save time, not something a static per-field schema can check. **Gotcha if you touch this**: a `superRefine` issue on a whole `useFieldArray`'d array (e.g. `path: ['steps']`, not `['steps', i, 'value']`) lands at `errors.steps.root.message`, not `errors.steps.message` — RHF reserves the plain array key for per-row errors.

Every componentized dropdown uses `ThemedSelect.tsx` (`src/renderer/src/components/shared/`), built on `@radix-ui/react-select` — a real accessible listbox (keyboard nav, typeahead) instead of a native `<select>`, styled via `.select-trigger`/`.select-content`/`.select-item` in `style.css`. This replaced the old `.select-wrap` + absolutely-positioned `<svg class="select-chevron">` workaround (the native arrow doesn't respect custom padding and renders visibly off-center against our styling) for every `<select>` owned by a React component — EditorModal's shell picker, PipelinesModal's edge-condition picker. The header's plain, non-React sort-mode `<select>` (`index.html`, wired via `modules/dom.ts`/`app.ts`) still uses the old `.select-wrap` pattern and a real native element — folding it into `ThemedSelect` would mean mounting a new React root into a static container (like `legacyMounts.tsx` does for `SnippetList`/`TagFilters`/`FavoritesBar`), a bigger change than a library swap, left for whenever that header control itself gets ported. If you add another componentized `<select>`, reach for `ThemedSelect` rather than a native one wrapped in `.select-wrap`.

**`[hidden]` vs. author CSS**: a rule as plain as `.field-row { display: flex; }` permanently defeats the `[hidden]` attribute's default `display: none`, because author stylesheets always win over the user-agent stylesheet regardless of selector specificity or source order. `style.css` has a blanket `[hidden] { display: none !important; }` near the top specifically to make `[hidden]` reliable everywhere in this app — if you ever see a `hidden`-toggled element stubbornly stay visible, check whether a class on it sets `display` and either drop that class in favor of `[hidden]`, or give the row its own non-conflicting class the way the schedule-type field-rows use `.schedule-field-row` instead of the generic `.field-row`. Don't reintroduce a `display`-setting class on an element that's also toggled via `hidden`.

### Windows-specific window setup (`src/main/window.ts`)

The launcher window is `frame: false` + `transparent: true` with CSS-drawn rounding/shadow (`.app-shell` in `style.css`), created `show: false` and only ever shown via `showWindow()`/`toggleWindow()` (hotkey, tray, or IPC) — don't flip `show: true` in committed code, that's a manual-testing-only knob. `hasShadow: false` and `thickFrame: false` are required on `BrowserWindow` — the default native shadow/thick-frame style paints a black rectangular artifact behind a transparent frameless window on Windows because it doesn't composite the alpha channel correctly. Don't re-enable them without re-verifying the corners. Neither disables edge-drag resizing, though — Chromium's own frameless-window resize hit-testing near the borders is independent of the native thick-frame style, so plain `resizable: true` is enough on top of `frame: false`.

**The window is user-resizable** (`resizable: true`, `minWidth`/`minHeight` = `MIN_WINDOW_WIDTH`/`MIN_WINDOW_HEIGHT`, currently 520×440 — see `window.ts`'s own comment for how that floor was picked: below it, the header's search-icon + 7 icon-buttons row alone needs ~325px, and `.search-input`'s CSS needs `min-width: 0` — the flexbox default `min-width: auto` otherwise refuses to shrink a text `<input>` past its browser-defined intrinsic size, which is what pushes sibling buttons off the header to be clipped by `.app-shell`'s `overflow: hidden` once the window gets small enough). The chosen size is persisted to `app-settings.json`'s `windowSize` (debounced 400ms on the `resize` event, flushed immediately on `close` as a backstop) and restored on the next launch, clamped to the current minimum in `createWindow()` in case it was saved by an older build with a smaller/no floor. `showWindow()`'s re-centering uses the window's *actual current* size (`getSize()`), not the original `WINDOW_WIDTH`/`WINDOW_HEIGHT` defaults, so a resized window keeps re-centering correctly on every show/hide cycle instead of snapping back toward where a 760×620 window would have centered. Content reflow needed no real work beyond the `.search-input` fix above — `.app-shell` and most of its children were already flexbox/`%`/`vh`-based (a side effect of the UI-scale feature needing relative sizing anyway), not hard-coded to the original fixed window size.

The tray/window icon is generated at runtime by a hand-rolled PNG encoder (`icon.ts`'s `buildIconPng` — raw RGBA scanlines + `zlib.deflateSync` + manual chunk/CRC32) rather than shipped as an asset file, so the app has zero external image dependencies. **The packaged `.exe`'s own icon is a separate thing** — electron-builder needs a real `.ico` file on disk at pack time (a `NativeImage` won't do), which `build/generate-icon.js` produces via the same circle-badge drawing logic (plus a touch of edge anti-aliasing, genuinely necessary once the same hard-edged math is blown up to a 256×256 icon) at 16/32/48/256px, packed into one `.ico` container. Wired in via electron-builder's `beforePack` hook (`build/beforePack.js`) regenerating `build/icon.ico` fresh before every pack, referenced by `build.icon` in `package.json`. `build/icon.ico` is gitignored (a build artifact, regenerated every run, not a checked-in binary) — but `build/*.js` is explicitly un-ignored (`.gitignore`'s `build/*` + `!build/*.js`) since `afterPack.js`/`beforePack.js`/`generate-icon.js` are real source. (This un-ignore is itself a fix — `build/` was entirely gitignored before, silently, so `afterPack.js` was never actually tracked despite this file documenting it as intentionally checked-in source; worth knowing if you ever wonder why a `build/` script isn't showing up in `git log`.)

The window hides (never closes) on blur/close/Escape unless `app.isQuitting` was set by the tray's Quit item — that flag is what distinguishes "hide" from "actually exit" throughout `src/main/`.

### Global hotkey (user-configurable) (`src/main/hotkey.ts`)

`registerHotkey(accelerator)` is the only place that calls `globalShortcut.register`/`unregister` — it unregisters whatever's currently active, tries the new one, and rolls back to the previous accelerator on failure (never leaves the app with *no* working hotkey without the caller finding out via its boolean return). At startup, `src/main/index.ts` tries the user's saved `appSettings.hotkey` first, then falls through a defaults array. The `set-hotkey` IPC handler (`ipc.ts`) is the only thing that persists a new accelerator to `app-settings.json` — a successful *startup* fallback does not overwrite the saved preference, so a combo that's temporarily taken by another app doesn't silently erase what the user actually asked for. (Registration can also fail entirely in some sandboxed/remote-desktop environments — the app still runs, just tray-only, and logs a note about it.)

### Self-update (`src/main/updater.ts`)

Wraps `electron-updater`'s `autoUpdater` with `autoDownload`/`autoInstallOnAppQuit` both **off** — check, download, and install/relaunch are three separate, user-triggered actions (Settings → Updates), never something that happens on its own in the background. Same "nothing runs unless you click it" stance as the rest of this app, just applied to the app updating itself instead of a command running.

Update feed is **GitHub Releases on this repo**, configured via `build.publish` in `package.json` (`provider: "github"`, `owner`/`repo` pointing at `whosm1ke/ElectronBasics`) — `electron-builder` writes `latest.yml` (version + installer hash) into the release alongside the NSIS installer whenever a release is published (see the `npm run release` note under **Commands**), and `electron-updater` reads that file to decide whether a newer version exists. Since the repo is public, an installed copy needs no auth to check/download.

`checkForUpdates()` guards on `app.isPackaged` first — running via `npm start` has no `app-update.yml` (that file only exists inside a packaged app's resources, generated from the `publish` config), so calling into `electron-updater` from source throws a confusing low-level error instead of the friendly "updates only work in the installed app" message this checks for up front.

Every `autoUpdater` event (`checking-for-update`, `update-available`, `update-not-available`, `download-progress`, `update-downloaded`, `error`) is forwarded to the renderer over one `update-status` IPC channel rather than being the return value of the `check-for-updates`/`download-update` IPC calls — those calls just kick off the corresponding `electron-updater` call and resolve almost immediately; the actual result arrives later via the event. `useSettingsStore.ts` keeps the last-received status so reopening Settings mid-download shows where things actually are instead of resetting to "Check for updates."

`quitAndInstall()` explicitly sets `app.isQuitting = true` before calling `autoUpdater.quitAndInstall()` — same defensive pattern as the tray's Quit item (`tray.ts`) — because `window.ts`'s `close` handler intercepts and just hides the window unless that flag is already set, which would otherwise silently swallow the quit the installer needs.

## Clean code in this project

This codebase was deliberately refactored from three large files (`main.js`/`preload.js`/`renderer.js`) into the current one-concern-per-file layout, then migrated to TypeScript + React on top of that same layout — the file-per-concern discipline predates and survived the framework migration. When adding or changing code here:

- **One concern per file, named for that concern.** If you're about to add a second unrelated responsibility to a file (e.g. bolting scheduling logic onto `shell/exec.ts`, or UI-state for a new modal into an existing store), stop and give it its own file instead. A module in this project should be describable in one sentence — most of them are, in the comment at the top of the file. Keep that comment current when you change what a file is responsible for.
- **Imports go one direction — no cycles**, in the renderer especially: Node's CommonJS/ESM cycles hand back a partial (possibly empty) export, which is a nasty class of bug either way, and Vite doesn't paper over it. `SnippetList.tsx`/`Card.tsx` render and are imported by many leaf modules for their `refresh()`/component exports — none of those may be imported back by them. When two modules genuinely need each other's behavior (the batch-run case: cards need to trigger a run, batch needs the card list's `refresh()`), pull the shared part into a third, lower-level module neither original one needs to import back — see `useBatchStore.ts`, which both `Card.tsx` and `pipelineEngine.ts` depend on without either needing to import the other.
- **Cross-cutting notifications go through the event bus, not a direct call chain**, for anything not yet on a Zustand store: `lib/events.ts` wraps a plain `EventTarget`; a module that mutates snippets calls `emitSnippetsChanged()` and doesn't need to know or care who's listening. Reach for this (or a store subscription, for fully-ported pieces) over a direct import when the relationship is "something changed" rather than "I need this specific value/function back."
- **Main-process storage modules all follow the same shape**: `ensure*File()` / `read*()` / `write*()`, a `sanitize*()` that backfills missing fields so old or hand-edited JSON never breaks the UI, applied on both read and write. The read side goes through `json-file.ts`'s `readJsonFileSafe()` (BOM-stripping, corrupt-file preservation) and the write side through its `writeJsonFileAtomic()` (write-file-atomic under the hood — temp file + rename, so a crash/power-loss mid-write can't leave the real file truncated) — every `storage/*.ts` module's `write*()` goes through this rather than a bare `fs.writeFileSync(path, JSON.stringify(...))`. Copy `storage/variables.ts` or `storage/app-settings.ts` as a template for a new persisted concern rather than inventing a new pattern — and add the matching shape to `src/shared/types/`.
- **Renderer DOM lookups outside React live in `modules/dom.ts`, never a scattered `document.getElementById` elsewhere.** If a not-yet-React piece of code needs a new element reference, add it once to `dom.ts` and import `dom` where needed. Inside a component, use refs the normal React way instead.
- **No template strings standing in for a templating engine, in the parts of the app that are still imperative DOM** (`runEngine.ts`, `processEngine.ts`, `pipelineEngine.ts`'s DOM-adjacent bits) — build nodes with `document.createElement`, direct property assignment, small `innerHTML` fragments for static icon markup only, matching the original style. Inside a component, write normal JSX — don't hand-roll DOM construction there. (`menus.ts` used to be a third example of this — it's gone; `CardContextMenu.tsx`/`CopyAsDropdown.tsx` are real componentized JSX now, per the rule's own last sentence.)
- **Comments explain *why*, not *what*.** The codebase leans on short header comments (what a file owns, and any non-obvious constraint) plus inline comments only where the "obvious" implementation would actually be wrong (e.g. why `terminal.ts` can't just `spawn()` directly, why `windowsVerbatimArguments: true` is required, why the pipeline canvas and process-output streaming stay imperative). Don't narrate straightforward code line-by-line; do explain a decision that isn't self-evident from reading it.
- **Prefer extending an existing small module/component over growing one past its stated concern.** If a file you're editing is growing past a couple hundred lines and picking up a second concern, that's the signal to split it (a new store, a new `lib/` file, a sub-component), not to keep appending.
- **Prefer the latest stable version of a dependency, and avoid deprecated APIs**, consistent with how this migration was done (TypeScript 7's native compiler, Vite 7, React 19, current `electron`/`electron-builder`/`electron-updater`). When a peer-dependency range forces an older minor (e.g. `@vitejs/plugin-react` pinned to the last 5.x release that supports Vite 7, since 6.x requires Vite 8), leave a comment on the pin explaining the constraint so a routine bump doesn't get silently reverted.

## Development

```bash
npm install
npm start
```

`npm run typecheck` and `npm test` before committing anything nontrivial — there's no pre-commit hook enforcing either. After editing, `npm start` hot-reloads the renderer; a main/preload change triggers electron-vite to rebuild and relaunch automatically.
